# 1Padel.App — настоящая парная запись внутри /app/

Подготовлено 22.10.2026 поверх UstinKO/padel-core-service master `df81c33e3f4afb5aef3877e746d4977a7c252a9c` (после PR701).
Цель: действующий клиент https://1-padel.com/app/, а не новое приложение и не отдельная демонстрация.

## Задание и согласованные требования

1. Для DOBLES + AMERICANO_TEAMS (и legacy AMERICANO + DOBLES) заменить переход «Записаться на сайте» внутренним сценарием. Остальные форматы не расширять без проверки их правил.
2. Три варианта: «У меня есть партнёр», «Ищу партнёра», «Добавлю партнёра позже».
3. Искать в общей базе игроков сайта и приложения по имени, фамилии, телефону WhatsApp и Telegram. Подсказки при вводе любого из четырёх полей. При совпадении игрок выбирается явно, одно имя не означает совпадение личности. Исключать себя и уже занятых участников по правилам сервера.
4. Для нового партнёра нужны имя, фамилия и WhatsApp; Telegram необязателен. Почту не спрашивать и не требовать. Если контакты совпали с существующим игроком, сначала предложить выбрать его, не создавать дубликат. Выбранного существующего игрока передавать по ID, не менять его контакты.
5. Готовая пара, включая нового гостя, регистрируется сразу без подтверждения по email партнёра. Статус CONFIRMED или WAITLIST и позиция очереди только из ответа сервера. Не обещать место при заполненном событии.
6. Перед отправкой отдельный экран проверки: оба участника, событие, дата/клуб, стоимость за человека и двоих, фактический срок отмены. Без дополнительного чекбокса регистрации: текст условий и явная кнопка «Записать пару». Запись не списывает деньги.
7. Для SEARCH сохранить отдельное необязательное согласие на показ собственных контактов, по умолчанию выключено. Список ищущих партнёра и отправка предложения используют существующие серверные правила. Отправленное предложение не является подтверждённой парой. Принятие предложения и парная отмена пока через сайт.
8. Для ADD_LATER показать фактическое серверное правило: добавить до начала минус 24 часа. После срока одиночная заявка переходит в резерв; добавление партнёра в такой резерв разрешено, готовая пара занимает место по существующей очереди. Не приравнивать этот срок к изменяемому дедлайну отмены.
9. После готовой пары — отдельные кнопки поделиться в WhatsApp/Telegram со ссылкой `/app/?event=ID`. Пользователь сам отправляет сообщение в мессенджере. Автоматическую доставку WhatsApp/Telegram не реализовывать и не обещать; регистрация от доставки не зависит. Ссылка только открывает детали события, не записывает автоматически.
10. После операции обновлять «Мои мероприятия»; для будущих парных событий дать кнопку «Моя пара» для проверки статуса/добавления партнёра.
11. RU/ES/EN; телефонный экран, прокрутка подсказок, экранная клавиатура, закреплённая кнопка.
12. Сохранить Google/email-вход, восстановление сессии и существующие индивидуальные запись/отмену.

## Что уже есть на сервере и используется

В текущем master уже есть поиск нормализованного телефона/Telegram и регистрация гостевого партнёра без email с немедленным формированием пары. Это не нужно реализовывать повторно.

Использованы существующие защищённые маршруты:

- GET `/api/players/search?query=...&tournamentId=...`;
- GET `/players/tournaments/{id}/my-registration`;
- GET `/api/tournaments/double/{id}/looking-for-partner`;
- POST `/api/tournaments/double/{id}/register`;
- POST `/api/tournaments/double/{id}/register-solo`;
- POST `/api/tournaments/double/{id}/add-partner`;
- POST `/api/tournaments/double/{id}/propose-pair/{registrationId}`.

Поиск/запись используют текущую авторизацию. Не делать поиск игроков или собственные данные публичными.

## Единственное серверное дополнение в патче

В существующий GET собственной активной регистрации добавить поля:
`registrationId`, `status`, `waitlistPosition`, `registrationDate`, `isDoubleRegistration`.
Существующие `registered`, `partnerId`, `partnerFirstName`, `partnerLastName`, `hasRegisteredPartner` сохраняются.
Идентичность берётся из principal, а не тела клиента. При отсутствии активной записи `{registered:false}`.
Не возвращать токены приглашения, email или телефон партнёра. Изменений БД и серверной политики записи нет.
Клиент требует расширенный контракт и при его отсутствии показывает ошибку проверки, без выдуманного статуса.

## Защита от случайной повторной операции

Перед записью/добавлением/предложением перечитываются событие и собственная запись; изменения условий требуют повторной проверки. Смена аккаунта отменяет старый сценарий. Двойное нажатие блокируется.
При потерянном ответе, неожиданном статусе или обновлении токена после 401 POST не переигрывается: только GET проверки состояния. Старая одиночная заявка сама по себе не доказывает успешное добавление партнёра. Неизвестный результат предложения не объявляется успехом.

Ограничения: локальная блокировка неопределённого результата действует в текущем экземпляре клиента, это не серверная idempotency. Между GET проверки и POST остаётся обычное окно конкурентных изменений, окончательное решение за существующей транзакцией сервера. Повторный поиск выбранного партнёра ограничен серверными 15 результатами и может консервативно попросить выбрать другого при распространённых именах. Эти ограничения не обходить отключением серверных проверок.

## Файлы и применение

`pair-registration.patch` содержит исходники и тесты, без node_modules и скомпилированных файлов. Это проверяемая реализация на указанную базу; изучить и адаптировать к текущему master согласно обычным правилам репозитория. Не требуется слепое применение присланного кода: при ограничениях интеграции реализовать требования из этого README самостоятельно.

Ключевые файлы: `mobile-app/src/PairBookingScreen.tsx`, `pairBooking.ts`, `pairCopy.ts`, `BookingEntry.tsx`; маршрутизация `App.js`, `PlayerScreen`, `MyEventsScreen`, `AuthContext`, `auth.ts`; расширение собственного GET в `PlayerDashboardController`; контрактный Java-тест и клиентские тесты.

После ревью:

```sh
git apply --check pair-registration.patch
# применить/адаптировать после ревью
cd mobile-app
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build:site
cd ..
# запустить обязательные серверные проверки и сборку по AGENTS/CLAUDE/CI проекта
```

Сборка `build:site` обновляет `src/main/resources/static/app/`; обязательно включить актуальную сборку в итоговое обновление сервера. Исходники клиента и расширение GET должны выйти согласованно. Ссылки assets должны работать под `/app/` и `/app/?event=ID`.
